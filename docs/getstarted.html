Getting Started with Pane

Welcome to Pane — a modular, high-performance hypervisor orchestration engine. Pane gives you bare-metal performance with microVM convenience, blending Rust speed, KVM control, io_uring storage throughput, eBPF micro-segmentation, and Go's ease of integration.

Whether you're sandboxing a local tool, building a serverless SaaS platform, or running full VM stacks, this guide will get you up and running.

1. Local Sandboxing (The Solo Developer flow)

For local development or command-line testing, Pane supports a lightweight Firecracker backend designed for direct kernel booting. It bypasses heavy bios/bootloaders, booting a Linux kernel in sub-1ms.

Prerequisites

Make sure your development machine has KVM enabled and you have read/write access to /dev/kvm:

ls -l /dev/kvm
# If needed, add yourself to the kvm group:
sudo usermod -aG kvm $USER

Spawning your first microVM

Using the Go gRPC client or by calling the FFI functions directly, you can boot a microVM.

package main

import (
	"context"
	"fmt"
	"log"
	"time"

	pb "pane/pane-api/proto"
	"google.golang.org/grpc"
	"google.golang.org/grpc/credentials/insecure"
)

func main() {
	// 1. Connect to the Pane gRPC daemon UNIX socket
	conn, err := grpc.Dial("unix:///run/pane.sock", grpc.WithTransportCredentials(insecure.NewCredentials()))
	if err != nil {
		log.Fatalf("Failed to connect: %v", err)
	}
	defer conn.Close()
	client := pb.NewPaneServiceClient(conn)

	ctx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
	defer cancel()

	// 2. Boot a microVM with a direct kernel boot config
	resp, err := client.Spawn(ctx, &pb.SpawnRequest{
		Id:          "sandbox-vm-1",
		KernelPath:  "/path/to/vmlinux",
		RootfsPath:  "/path/to/rootfs.img",
		VcpuCount:   1,
		MemSizeMib:  128,
		BootArgs:    "console=ttyS0 reboot=k panic=1 pci=off",
	})
	if err != nil {
		log.Fatalf("Failed to spawn VM: %v", err)
	}

	fmt.Printf("VM Booted! ID: %s, Vsock CID: %d, PID: %d\n", resp.Id, resp.VsockCid, resp.Pid)
}

2. Architecting for Scale (The High-End Production flow)

When building a high-density host environment, you need resource isolation, network micro-segmentation, and instant scalability. Pane handles this without heavy hypervisor layers or complex corporate setups.

Resource Controls via cgroup v2

Pane automatically creates a dedicated cgroup directory for every VM. You can dynamically apply CPU scheduling, memory limits, and process limits:

  • Memory Caps: Enforce tight bounds (e.g., 256MB RAM). If the guest runs Out of Memory, KVM traps the process inside the cgroup, protecting the host system from crashing.
  • CPU Quotas: Limit CPU shares to ensure fair scheduling across co-located tenants.

Network Micro-segmentation with eBPF (aya)

Instead of clogging host routing tables with thousands of complex iptables or nftables rules, Pane compiles a custom eBPF packet classifier (pane_filter.bpf.c) and attaches it directly to the host TAP device ingress using Traffic Control (TC).

  • VMs are assigned to group IDs.
  • eBPF inspects IPv4 packet headers on the host interface.
  • Communication between VMs of different groups is dropped at the lowest kernel layer with zero overhead.

Instant Cloning (Forking)

For serverless scaling, boot-up time is critical. Rather than starting a VM from scratch, Pane lets you freeze a running VM, write its memory and device state to a snapshot, and instantly fork clones:

  • Benchmark: Clone 50 VMs from a single parent snapshot in under 2 seconds total wall-time.
  • CoW Memory: Uses Copy-on-Write memory mapping to share parent pages until modified, minimizing RAM consumption.

2.5 Running OCI/Docker Container Images inside MicroVMs

For modern containerized workloads, Pane features Container Compatibility (pane-ctr). It lets you run Docker/OCI container images inside highly secure KVM microVMs with sub-second boot times.

How the Conversion Pipeline Works

  1. Layer Pulling: Pane uses go-containerregistry to fetch the OCI image manifest and layer tarballs from the registry (e.g. Docker Hub).
  2. Layer Flattening: The layers are sequentially extracted into a host temporary directory. Standard OCI whiteouts (.wh.<file>) and opaque markers are resolved to correctly handle deleted files and folders.
  3. Agent Injection: The static host pane-agent binary is injected into the rootfs as /usr/sbin/pane-agent.
  4. PID 1 Init Injection: A custom minimal, statically-linked C-based bootstrapper is compiled and injected as /init.
  5. ext4 Disk Formatting: The flattened rootfs directory is formatted into a raw ext4 filesystem disk image using host-side mke2fs -d.
  6. Kernel Provisioning: Pane automatically downloads and caches a precompiled guest Linux kernel (ELF uncompressed vmlinux) to boot the microVM.

Step 1: Pull and Convert a Container

Simply use the docker:// scheme prefix to pull any container image:

# Pull and automatically convert nginx to a Pane bootable VM image
pane pull docker://nginx:latest

This outputs a bootable virtual disk containing the flattened rootfs, static init, and cached Firecracker kernel defaults inside /var/lib/pane/images/nginx-latest/.

Step 2: Run the Converted Container

To run the container, use the image name directly. You can override memory, CPUs, or add raw QEMU passthrough args:

# Spawn the container-derived microVM
pane run --name nginx-container alpine-latest

At boot, the statically linked guest /init mounts API filesystems, spawns the vsock agent loop, reads /oci-config.json, sets up environment variables, changes directory, and execs the container's OCI entrypoint as PID 1.

3. Running Custom ISOs & Windows on Pane

Pane's default Spawning state leverages Firecracker for speed, but the C-layer hypervisor pane-vmm contains a fully functional QEMU Backend designed to run custom ISOs, full operating systems (like Ubuntu Server), or Windows.

In Pane v0.2, you no longer need to modify C code or recompile the hypervisor to configure QEMU. A robust config builder compiles the QEMU argv string dynamically based on CLI flags, yaml configuration files, or cached image metadata.

Step 1: Register and Cache your ISO

Place your ISO image and any drivers (like VirtIO drivers for Windows) in the local folder. Use pane pull to register the image in Pane's local cache:

# Register Windows Tiny10 ISO and package it with VirtIO drivers
pane pull tiny10

This copies the ISO, configures default drivers (virtio-blk, virtio-net), and attaches the VirtIO driver CD-ROM via merged metadata.

Step 2: Start the VM with CLI overrides

To allocate more memory, vCPUs, or customize arguments dynamically, use the CLI flags:

# Run Windows VM with 4 vCPUs, 4GB RAM, and VNC server enabled
pane run --name win-vm-01 --cpus 4 --memory 4GiB tiny10

Under the hood, Pane merges the default profile, cached tiny10 spec, and your CLI flags to construct the correct QEMU command-line parameters:

qemu-system-x86_64 -enable-kvm -m 4096 -smp 4 -drive file=/var/lib/pane/images/tiny10/v1.0/disk.iso,format=raw,if=virtio -cdrom /var/lib/pane/images/virtio-win.iso -vnc :1

Tip: You can VNC to port 5901 of the host to access the graphical installation interface.

Step 3: Dry-Run for Debugging

To inspect the generated argv list before spawning the VM, use the --dry-run flag:

pane run --dry-run --cpus 4 --memory 4GiB tiny10

This runs the entire merge precedence logic and prints the exact spec configuration and backend arguments without executing anything.
